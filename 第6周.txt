第6周：数据建模——决定系统命运的不是页面，是数据
第5周你已经会画架构图、写ADR、分清同步和异步。
但如果数据没想清楚，再好的架构图也只是纸上谈兵。
本周把项目二的地基打牢：表怎么拆、接口怎么约定、Trae Skill 怎么固化工程规范——这才是“超级个体 = 产品经理 + 架构师”里，架构师真正吃功夫的一块。
课前你可能会问
“表不是让AI自动生成就行吗？为什么还要自己设计？”
“Supabase已经很好用了，还要学什么存储选型？”
“接口要自己写？AI不能直接生成吗？”
下面五节会逐一回答。记住一句总纲：
数据模型决定了你以后能问系统什么问题；接口契约决定了前后端和AI能不能长期和平共处。
一、讲授内容
1.1 开场冲击：差距不在页面，在“数据有没有想清楚”（约5分钟）
先做一个残酷对照。
两份作业可能页面一样好看，但三个月后：
A同学：用户、笔记、标签、摘要任务、向量检索各归其表，改功能只动一小块；
B同学：28个字段全塞进users，每加一个功能就改表结构，查询越来越慢，AI生成的接口前后对不上。
第二种不是“不规范”，是用数据库设计锁死了产品能力——这在《数据密集型应用系统设计》（DDIA）里有一句狠话可以借来记：
数据模型不仅描述数据长什么样，还决定了你能多容易地让数据随业务演变。
本周所有内容，都服务于一件事：让你的项目二“以后还能改、还能长”。
图题：页面很炫 vs 地基很稳——谁走得更远
💡 试想这样一个场景：一张"万能表"把28个字段全塞进去——短期能跑，长期为什么痛？今天你会知道痛在哪一根支柱上先断。
1.2 北极星：可靠、可扩展、可维护——三根支柱（约10分钟）
DDIA里三个英文词听起来吓人，换成人话就是你看系统时的三副眼镜：
现场想一个失物招领小场景：
如果把图片、标签、状态、认领记录全塞进同一张“万能表”，现在也许能跑；但一旦要查“某类物品本周认领率”、要做消息通知、要加审核状态——你会发现要么查不出来，要么每次改功能都像拆楼。
金句：三张表设计得好，胜过十张页面做得炫。
以后你每画一张表、每一个接口字段，都可以自问：这更像在加固可靠性、扩展性，还是可维护性？代价是什么？（这和第5周的 Everything is a trade-off 是同一套思维。）
图题：DDIA三根支柱托住你的数据库设计
1.3 三种数据，三种存法——最小选型地图（约15分钟）
本课默认主存储仍是 Supabase（PostgreSQL），但你要建立一张最小地图：不是什么东西都适合塞进同一种“格子”里。
决策题（课上会一起拆）：你在做**「课程笔记智能整理」**，至少应想到四类“落脚点”：
用户（谁）
笔记（内容主体）
标签/分类（结构化检索）
向量索引（“这句像哪篇笔记？”）
它们可以都在 Postgres 里落地（表 + 可选 pgvector），关键是：不要假装它们是同一种东西而塞进一张表。
在Trae里你可以这样开题（再一起人工改）：
我在做「课程笔记智能整理」校园产品，使用 Supabase Postgres。
请给出用户、笔记、标签、摘要任务、向量检索相关的表结构设计建议：
字段、类型、主外键、可空约束，并解释每张表对应哪类数据、为什么拆分。
金句：选型不是为了炫技，是为了让正确的查询在未来依然便宜。
图题：三种数据三种存法——关系·文档·向量并排认知地图
1.4 契约优先：先定义接口，再让AI写代码（约10分钟）
很多同学的真实顺序是：
AI先生成接口 → 前端凑合对接 → 一改需求全盘乱套
架构上更稳的顺序是：
先写契约（输入/输出/错误/状态码）→ 再让Trae按契约生成后端与前端
契约就是各模块之间的法律：不是写给老师看的说明文，而是机器和人都能对齐的规格。
最小契约里建议固定这几块：
课上演示母题：「创建笔记摘要」——不需要你从空白写契约，而是给Trae一条母提示词，让它帮你出初稿，你来审改。
接口契约生成·母提示词（直接粘进Trae）：
我的项目是「{你的题目}」，使用 Supabase Postgres。
请为「{某核心功能，如：为一篇笔记生成AI摘要}」设计一份接口契约：
1. 路径与HTTP方法
2. 请求体：字段、类型、是否必填、示例值
3. 响应体：成功时的JSON结构
4. 错误返回：统一格式 { code, message, details? }，列出2-3种常见错误
5. 异步边界：该接口是同步返回结果，还是返回taskId由前端轮询？给出你的建议和理由
请用 Markdown 表格输出，方便我审查和修改。
拿到初稿后，你的工作是审改——删掉不需要的字段、补你的业务约束、确认异步边界是否合理。然后用下一条指令让Trae按你审改后的契约生成代码：
以下是我审定的接口契约（粘贴）。
请严格按契约生成后端路由骨架 + 前端API调用封装，不要增删契约中未定义的字段。
金句：Spec 不是文档，是施工蓝图。 AI出初稿，你审定蓝图，再让AI按图施工。
图题：契约优先——蓝图在前，代码在后
1.5 Trae Skill：让工程规范变成 AI 的执行习惯（约10分钟）
当堂演示：把「契约先行」固化成 Trae Skill（3分钟）
Trae 右上角 ⚙️ 设置 → 规则和技能 → 创建，填入：
技能名称：契约先行
描述：生成接口时先走契约流程，避免前后端对不上
触发词：生成接口 / 写接口 / 定契约
步骤：
1. 先问用户：要为哪个功能写契约？（功能名 + 所属项目）
2. 用以下模板生成接口契约初稿（路径/请求/响应/错误/异步边界），Markdown 表格输出
3. 请用户审改确认
4. 审改完毕后，严格按确认后的契约生成后端路由骨架 + 前端调用封装，不增删字段
保存后，以后在 Trae 里只需说**"生成接口"**，AI 就自动走完这四步，不会再绕过契约直接裸写代码。
这就是"指挥官"思维的工具化：你把工程纪律写成 Skill，AI 帮你执行，你专注审查。
二、课堂实战练习
练习目标：把项目二从“先画页面”扳回**“先建模、先定契约、再写能力接口”**——走出教室时，你应能指着架构图说清：最重要的数据对象是谁、接口长什么样。
练习一：Schema体检（约10分钟）
拿出你的项目二题目。
列出 3～5 个核心数据对象（名词，不是页面）。
用箭头或一句话写出它们之间的关系（1对多、多对多……）。
对照三根支柱各提一个风险：哪里可能不可靠？哪里可能先撑不住？哪里最难维护？
图题：从“页面想法”反推到“数据对象气泡图”
练习二：Trae辅助建模（约10分钟）
在Trae中对项目仓库（或新建设计文档）输入：
请为我的校园产品「{你的题目}」设计 Postgres（Supabase）表结构：
至少3张表，包含字段类型、主键、外键、是否可空、必要索引建议。
并解释：每张表对应哪个核心对象？为什么这样拆表而不是合并？
拿到初稿后，你必须亲自改一版：删掉明显冗余、补上你认为的业务约束（如唯一性、状态枚举）。
⚠️ 防坑提示
AI 可能把向量字段塞进每张表——想想是否真的需要、是否应单独索引策略。
外键、级联删除要不要开？先问“删用户时笔记怎么办”，再决定。
让 Trae 引用你的 PRD 五要素，避免它臆造功能。
练习三：契约先行（约10分钟）
任选一个核心功能（如：创建笔记、发布二手、提交组队需求）。
把上面1.4节的接口契约生成·母提示词粘进Trae，替换{}占位符，让AI出初稿。
你来审改：删冗余字段、确认错误格式、标注异步边界。
审改完毕后，再下指令让Trae严格按你的契约生成代码：
以下是我审定的接口契约（粘贴审改后的版本）。
请严格按契约生成后端路由与前端 API 封装，不要添加契约中未定义的字段。
💡 关键不是你能不能写出完美契约，而是你能不能看出AI初稿的问题并改对——这就是"指挥官"的能力。
图题：契约像合同——双方（前端/后端）按条款对接
练习四：创建「契约先行」Trae Skill（约15分钟）
把 1.5 节示范的「契约先行」Skill 搬进你自己的 Trae，让它替你主持每一次接口设计。
在 Trae 右上角 ⚙️ → 规则和技能 → 创建。
把 1.5 节的「契约先行」Skill 模板原样粘入，将触发词改成你项目惯用的说法（如"定接口"）。
保存后立即测试：在 Trae 对话里说出触发词，看 AI 是否按"问功能→出契约→等审改→生成代码"四步走。
截图保存（触发词 + AI 执行结果），作为本周作业提交物之一。
⚠️ 防坑提示
触发词要具体（如"定接口""写契约"），不要太宽泛（如"帮我写"），否则会意外触发。
Skill 创建完后记得在当前项目仓库里测一遍，而不只是在空白对话测。
练习中请刻意观察（为第7周埋伏笔）
哪一个核心流程明显是多步骤？（例如：上传 → 识别 → 清洗 → 入库）
哪些步骤应该写死顺序，哪些步骤需要交给 AI 判断下一步？——下周会从这里切开讲。
三、课后作业
作业一（必做）：【数据架构师】项目二数据模型与接口契约
目标：把系统地基搭稳，避免后期返工。
完成以下内容：
最终版核心 Schema：至少 2 张表，建议 3～5 张；写清字段类型、主外键、是否可空、必要索引/约束说明。
不必从零手写表结构：可用 Trae 生成初稿——直接复用**「练习二：Trae辅助建模」中的提示词（或见文末附录 A**），再结合你的数据对象清单审改；提交的是你审定后的版本，并在文中简要说明相对 AI 初稿你改了哪些关键点（3～5 条即可）。
接口契约文档：至少 2 个核心接口；写清请求体、响应体、错误格式（可 OpenAPI 片段或 Markdown 表格）。
使用课上「接口契约生成·母提示词」（见 1.4 节或文末附录 B）：对每个接口各跑一遍，得到初稿后审改定稿再提交；不要求你从空白起草。若两个接口功能差异大，把母提示词里的「某核心功能」分别换成不同描述各跑一次即可。
提交到云邮平台：一份 Markdown（Schema 说明 + 审定后的接口契约 + 内嵌或附录 Mermaid 架构图；建议附 **「AI 初稿 → 我改了什么」**简短清单，每块各 3～5 条，证明你做过审查）
评分重点：不是表越多越好，而是——拆表理由是否说得清、契约是否自洽、图上是否看得出数据从哪来到哪去；能看出你对 AI 初稿做过有理由的审改，比“一字未改粘贴”得分更高。

可靠（Reliability） | 出错了还能不能正确服务？ | 脏数据、重复提交、并发写入时，表结构和约束能不能兜住？

可维护（Maintainability） | 三周后的你/队友还能不能看懂、敢改？ | 字段含义清楚吗？关系是一眼能画出来，还是全靠猜？
