第7周：工作流编排——哪些步骤写死，哪些判断交给 AI
第6周你把数据建模和接口契约做好了，系统有了轨道。
但用户一次点击背后，往往是一串步骤：上传 → 识别 → 清洗 → 入库 → 通知……

一、讲授内容
1.1 同一个功能，两种命运（约5分钟）
想象「校园失物识别」这个功能：
演示版：上传图片 → 调一次大模型 → 蹦出一段文字 → 像魔法，但三周后改不动
产品版：
上传 → 校验格式/大小（代码）
     → OCR 识别文字（调用外部 API）
     → 大模型分类「电子产品/证件/衣物…」（LLM 节点）
     → 写入数据库（代码）
     → 触发订阅通知（事件）
第二种不是「功能更多」，而是把不确定性拆到合适的格子里：有的格子稳定可测，有的格子模糊可迭代，失败了知道卡在哪一站。
一次 Prompt 解决一切，等于把所有风险堆在同一个黑盒里——出事了你不知道哪里错。
魔法黑盒 vs 流水线——谁更像真实产品
1.2 最重要的区分：Workflow vs Agent
2026 年工业界最重要的一个工程共识，来自 Anthropic 生产级 Agent 指南：
工业界共识（Anthropic）：能用 Workflow 解决的，绝不用全自主 Agent。
原因很简单：Agent 自主性越高，出错时越难定位，成本越高，用户越没有安全感。
对你的项目意味着什么？
你的校园产品大概率适合 Workflow 为主：
上传 → 入库 → 通知：全部代码控制
其中「分类」「摘要」「意图识别」这几步：代码调用 LLM，LLM 做节点内判断
Trae SOLO 帮你跑工程任务（补日志、重构函数）：它是 Agent，但你给它划了边界，所以可控
不是所有 AI 驱动的任务都要用 Agent；Workflow + 少量 LLM 节点，往往更稳、更安全、更容易上线。

吴恩达在 BUILD 2024 发表了一个极有影响力的判断：
AI 的未来不在于让单个 Agent 自由行动，而在于把它嵌进设计好的工作流。
他总结了四大 Agentic Workflow 设计模式，从简单到复杂：
这周最重要的是①和②——它们是 Workflow 节点里 LLM 最常做的两件事。
Tool Use 的工程含义（每个能力节点的本质）：
Workflow 里的每一站，如果需要访问数据库、调用大模型、调用外部 API——就是一次 Tool Calling。
第6周你用 Trae Skill 固化了「如何写契约」，第7周的工作是把多个 Tool Calling 节点串成有序的流水线。

Workflow = 代码铺的轨道 + 多个 Tool Calling 节点 + LLM 在某几站做判断（Reflection/意图识别/分类）

1.4 架构风格选型 + 状态机
选什么架构风格组织你的工作流？
第5周你学过三张认知地图。本周把它们用于工作流选型：
最小决策卡（写到你的架构文档里）：
步骤固定、数据单向流动         → Pipeline（优先考虑）
需要通知/异步回调/多方解耦     → Event-Driven（解耦用）
普通 CRUD，没特殊需求          → Layered（默认）
多步骤 AI 任务，优先用管道思维画图；「通知别人」的部分，优先用事件思维解耦。
工作流状态机：流水线要有记忆
多步骤任务的真实痛点：「跑到一半失败了，重启之后从哪里继续？」
答案是状态机——在数据库里建一张 tasks 表，让流水线有记忆：
这样失败时：用户看到「卡在识别步骤，正在重试」；开发者打开数据库，一眼看出在哪一站、错误是什么。
状态存在数据库里，流水线才有记忆；没有状态表的多步骤任务，每次重启都从零开始。
这也是 DDIA「可维护性」支柱在工作流里的直接体现——第6周讲过，第7周用上了。

1.5 Trae SOLO：边界内的 Agent 执行器
现在你理解了 Workflow vs Agent 的区分，SOLO 就很好理解了：
SOLO = Agent 模式（LLM 自主决定步骤），但你通过任务描述给它划了边界，让它在限定范围里自主执行。
怎么进入：界面左上角，切换模式至 SOLO。
界面从左到右：任务管理面板 → AI 对话面板 → 工具面板（编辑器/文档/浏览器等）。
两种智能体，要会选：
SOLO 的执行流程就是 Planning 模式的实例：
你写清目标 → SOLO 拆解 TODO（Planning）
           → 读仓库/写代码/调命令（Tool Use）
           → 汇报结果（你审 Diff）
你务必做的三件事：
写清禁区：【禁止】不改 Schema / 不提交密钥 / 不删数据——边界不清，SOLO 会「自由发挥」
审 Diff 再接受：对话里点「查看变更」，先看 diff，不要盲目接受
按验收标准检查：SOLO 说「完成了」≠ 你的标准也通过了
SOLO 再强，也在走「计划→工具调用→汇报」的 Planning 模式；你的工作是把目标和禁区写在任务说明里，审 Diff、拍板。
演示母题（可照着用）：
【模式】SOLO Coder
【目标】为项目中所有对外 API 路由增加统一 try/catch 和日志（logger 名称统一）
【范围】仅修改后端路由相关文件
【禁止】不改数据库 Schema；不改接口契约字段；不提交任何真实密钥
【验收】本地可启动；触发一个错误时，返回契约中定义的错误格式
【停止】若测试无法运行，列出缺失依赖，不要编造测试结果
SOLO 就是 Planning 模式的产品化——任务说明→TODO→Tool Use→你审 Diff
1.6 Human-in-the-loop：自动化不能越权
工作流里必须建立**「红色按钮」思维**——不是所有步骤都应该自动化：
Human-in-the-loop 在代码里是什么样的？
# 伪代码示意：高危步骤加审批节点
if action.risk_level == "HIGH":
    approval = await request_human_approval(action)  # 推送给操作员确认
    if not approval.confirmed:
        return {"status": "cancelled", "reason": "human rejected"}
# 确认后才执行
await execute_action(action)
失败不是意外，是常态。好的工作流设计的不是「永远成功」，而是：
失败可见：状态落在 tasks 表，用户看到「卡在第几步」
失败可恢复：允许从 current_step 重试，不必从头跑
失败有上限：重试次数封顶，重试风暴比单次失败更可怕
没有「失败后怎么办」的工作流，不叫自动化，叫赌博。

② Reflection（自我反思） | LLM 生成后再让它/另一个 LLM 批改 | AI 写完失物描述摘要，再让它对照原文「打一版分」，不够好就重写 | ✅ 可在作业中尝试
③ Planning（规划） | LLM 先把大任务拆成子任务列表，再依次执行 | 给 Trae SOLO 一个目标「完善项目的错误处理」→ 它先输出 TODO 再逐条执行 | ✅ 这就是 SOLO Coder 在做的事
④ Multi-Agent（多智能体） | 多个 Agent 分工，输出互相传递 | 一个 Agent 审需求、一个写代码、一个跑测试、一个负责代码审查 | ⚠️ 项目三再深入，现在理解概念即可

心智模型 | 像什么 | 选它的信号 | 画图时画什么
Pipeline（管道） | 工厂传送带：上一步输出是下一步输入 | 步骤有顺序、数据单向流动、每步无状态 | 站名 + 输入输出 + 失败在哪站停
Event-Driven（事件触发） | 广播系统：某件事发生了，谁关心谁响应 | 需要通知、异步回调、多方解耦 | 事件名 + 谁发布 + 谁订阅 + 主链路解耦
Layered（分层） | 楼层结构：每层只管自己的职责 | 普通 CRUD 产品，分层就够了，不需要流水线 | 层与层之间的调用关系
