# F1 原生 App 信息架构与交互设计草案

**状态：**用户已确认四入口、少框线布局、借鉴网站的视觉及连体 FP 标识。可点击评审原型仍位于 `docs/design/native-app/index.html`，其八类页面使用示例数据。独立 Kotlin / Compose 公开数据试用版 `0.1.0` 现已生成 APK，设备运行尚未验收；原生构建证据见 `docs/qa/native-android-mvp.md`。

**用户要求：**软件内部界面和交互需要重新设计，现有网站的页面结构不适合直接移植到手机 App。

**已确认的视觉约束：**不使用大量边框、卡片和嵌套容器包裹信息，避免浪费手机横向空间；其余按本文结构推进。

**视觉修订（2026-10-27）：**大部分视觉语言沿用网站，重新组织手机交互。复用网站现有字体、红色强调线、赛事标题、轻量网格、车手头像和车队配色；撤掉第一版过大的 ITALIA 装饰标题，降低空白与标题占比，恢复更紧凑、专业的数据排版。网站的多层卡片和边框不照搬到手机端。

**品牌标识：**用户指定顶栏品牌为 **FrankPitwall**。原型已采用独立绘制的 FP 图形与路径化字标，提供透明 SVG / PNG 及浅色、深色版本，资产位于 `docs/design/native-app/brand/`。后续原生顶栏沿用此品牌；这次不更改现有网站名称、应用包名或发布配置。

FP 图形根据用户反馈进一步联动：两个字母共用竖笔，上横和中横连续接入 P 的闭合环，使用一致斜切形成一体化轮廓，保持小尺寸辨识度。

**产品方向：**Android 优先，以“打开 App 查看当前比赛周末，并按需查看成绩和分析”为主要使用路径。保留 F1 数据产品的品牌与专业性，重新组织导航、信息密度和触摸操作。这个主要任务是当前设计假设，后续可根据原型反馈调整。

## 1. 现有结构与需要解决的问题

依据源码进行结构检查，未将本次检查描述为设备上的视觉验收：

- `src/components/Layout.tsx` 包含首页、新闻、积分、赛事、进站榜、车手、车队、赛道和设置九个一级入口；手机端需要更少、更稳定的主导航。
- `src/pages/Race/RaceLayout.tsx` 将赛事概览、排位解构、比赛解读、冲刺周末、周末情报作为同级页面。
- `src/pages/Race/RaceResults.tsx` 内部还有场次 Tabs 和成绩表；手机上需要避免把“内容分类”和“场次选择”叠成多层标签栏。
- 当前分析页含大表格和多个分析模块；原生端需要优先回答当前问题，再进入单项分析。
- 网页的悬停预加载、HTML Tooltip 和表格交互不能作为触屏操作的前提。

## 2. 信息架构

最终功能结构采用四个主入口；原型会展示完整架构，首个原生试用包只展示已实际实现的入口。

| 主入口 | 首要任务 | 内容归属 |
|---|---|---|
| 赛事 | 看当前/下一站，进入比赛 | 比赛周末、完整赛历、历史赛事、赛事相关新闻入口 |
| 榜单 | 看谁领先、差多少 | 车手积分、车队积分；进站榜作为后续独立子页 |
| 资料 | 找一个人、一支车队或一条赛道 | 搜索、车手、车队、赛道及其历史档案 |
| 我的 | 管理账号和使用偏好 | 登录、权限状态、时区、主题、语言、缓存与隐私说明 |

备选方案比较：新闻作为首页适合内容阅读，但会拉长成绩查询路径；分析工作台作为首页适合少数重度用户，但会增加首屏选择负担。当前选择以赛事为中心，榜单与资料保持直接入口。

规则：

- 手机使用底部导航；详情页进入独立页面，保留系统返回。
- 返回恢复原先的赛季、滚动位置和筛选；切换主入口后保留各自浏览状态。
- 赛季选择属于当前赛事或榜单上下文，不在一个页面切换后静默改变另一个已打开的历史详情。
- 资料搜索从资料入口进入，不给每一页添加搜索框。
- 登录用于访问需要身份的内容；不在启动时用登录页阻挡已允许公开访问的数据。
- 新闻、进站、预测等现有模块均保留明确的目标位置；暂未实现的模块不作为可点击空入口发布。

## 3. 八个关键页面

### A. 赛事首页

**主要任务：**五秒内知道当前是哪一站、下一个场次何时开始、成绩是否可查。

首屏自上而下：

1. 简短标题“赛事”和当前赛季选择。
2. 当前/下一站赛事：名称、地点、状态、最近一个相关场次的用户时区时间。
3. 唯一主要动作：“查看周末”；直接进入具体比赛。
4. 接下来几个场次的纵向时间线；可进入完整赛历。
5. 最近完赛结果摘要及相关新闻入口，按后续阶段的数据与功能可用性出现。

赛前突出下一场次；赛后突出成绩入口；赛季结束显示赛季总结与最后一站。进行中只代表根据日程判断的赛段状态，不宣称实时计时，也不展示未经确认的直播数据。

### B. 完整赛历

**主要任务：**找到指定分站。

- 按时间排列的原生列表，状态明确显示未开始/已完赛/时间待定。
- 点击整行进入赛事；返回保持所在位置。
- 通过赛季选择切换历史赛历；切换时取消旧请求，避免出现跨赛季结果。
- 赛程变动以官方更新时间和实际数据为准，时间未知时不计算假倒计时。

### C. 比赛概览

**主要任务：**理解当前周末并选择下一项操作。

- 顶部仅保留返回、赛事简称和状态，完整赛事信息在正文第一部分。
- 内容导航精简为“概览 / 成绩 / 分析”，不把冲刺周末做成另一个一级模块。
- 概览展示周末场次时间线与简短赛道信息；冠军、杆位等摘要只在数据可用时显示。
- 新进入页面按比赛状态突出下一场次或已发布结果；用户开始浏览后不因后台刷新自动切走当前内容。
- 深层分析进入独立页面，返回恢复比赛上下文。

### D. 场次成绩

**主要任务：**快速找到车手名次与成绩。

- 顶部一个场次选择器，点击后通过底部选择面板选择正赛、排位、冲刺或练习赛；仅列出该周末实际安排的场次。
- 成绩与场次作为两个不同维度处理，不再叠加多排 Tabs。
- 列表行固定展示名次、车手/车队、核心成绩；必要时增加一项积分，较小宽度下积分移到次行。
- 退赛和未分类显示真实状态，不用数字补齐；排位赛按阶段显示成绩，展开后查看其他阶段。
- 点击车手行进入该场表现详情；完整字段按需展开，不要求横向拖动整张大表。
- 未开始、结果待发布、源数据缺失和请求失败分别呈现。

### E. 圈速对比

**主要任务：**比较选定车手的比赛表现。

- 从“分析”选择一个问题，例如圈速、轮胎策略或速度对比，每项进入独立分析页。
- 默认显示两名有数据车手；通过底部选择面板修改，不强制先完成复杂筛选。
- 图表下方显示选中圈的数据；点击或拖动选中位置，无需悬停。
- 每屏优先一个主图；数据表作为替代视图，支持 TalkBack 读取。
- 复杂缩放需要显式开启或独立全屏模式，避免与页面滚动和系统侧滑返回冲突。
- 圈速对比先做原型和性能验证；不存在数据时不展示模拟曲线作为真实分析。

### F. 积分榜

**主要任务：**比较排名、积分与落后差距。

- “车手 / 车队”分段切换，赛季选择位于标题区域。
- 一行展示名次、名称、积分及必要的次要差距信息；整行可进入档案。
- 不在列表上方重复展示大量冠军卡片和相同数据。
- 积分遵循现有官方数据契约；不按当前规则重新计算历史赛季。

### G. 资料入口

**主要任务：**找到具体车手、车队或赛道。

- 顶部资料搜索；“车手 / 车队 / 赛道”作为内容分类。
- 档案先显示身份与关键成绩，再按需进入历史赛季和比赛记录。
- 搜索、列表与档案返回保留查询词和位置；不将每个统计模块都做成横向轮播卡片。

### H. 我的

**主要任务：**管理会话与显示偏好。

- 账号状态和明确的登录/退出操作；会员说明仅表达现有服务端授予的权限。
- 主题、语言、时区、缓存和隐私使用原生设置列表。
- 登录、密码恢复和权限不足有独立流程；验证码和回调能力在认证阶段验证。
- 退出后清理私有内容和敏感会话，公开缓存按已有策略处理。

## 4. 核心交互约定

| 情况 | 操作与反馈 |
|---|---|
| 切换赛季、场次、车手 | 短选项用分段控件，长选项用底部面板，保留明确的当前选择 |
| 刷新列表 | 下拉刷新，并提供可被辅助功能访问的刷新动作；保留已加载内容 |
| 查看详细字段 | 点击进入详情或展开当前条目；不依赖长按或 hover |
| 请求失败 | 在相关模块内提示并重试，其他成功模块继续可用 |
| 离线 | 显示缓存与更新时间；未缓存的内容明确不可用 |
| 返回 | 优先交给系统导航，先关闭面板或键盘，再返回上层 |
| 会话过期 | 保存当前公开页面位置，引导重新认证，不把权限问题显示成无数据 |

## 5. 视觉和可访问性

- 默认采用平铺内容与原生列表，信息通过留白、文字层级、列对齐和少量分隔线分组。
- 页面正文只保留一层横向内边距，手机基线 16 dp；成绩列表、时间线和图表不叠加卡片内边距。
- 禁止“页面容器 → 卡片 → 小卡片 → 数值框”的嵌套结构；统计数字直接排列，列表行不各自加圆角外框。
- 边框仅用于确有必要辨认的输入、选择与弹层边界；允许系统底部面板和对话框，不能把“减少框线”误解为移除交互反馈。
- 主要动作、选中标签、可点击整行和焦点状态仍须明确；不靠给每条内容加框来表示可操作。
- 视觉方向：清晰的赛道数据工具，以列表、分区和稳定对齐为主，红色用于主要动作和关键强调。
- 从 `src/styles/design-tokens.css` 映射现有品牌、车队和状态色到 Kotlin 主题，不复制网页布局。
- 间距基线：4/8/12/16/24/32 dp；主要正文 16 sp、次要标签 14 sp、页面标题 22–24 sp、关键数字 28–32 sp，实际以字体缩放和内容适配验证。
- 视觉原型复用 `src/styles/fonts.css` 中的 F1 UI Sans、F1 UI Hanzi、F1 UI Display、F1 UI Mono 及其现有许可资源；标题使用 Display，成绩时间用 Mono，正文和中文使用现有中英文字体栈。正式 Kotlin 端按原生可支持的字体格式和中文覆盖验证后接入，保留系统字体回退。
- 深浅主题均有明确的文字对比；名次、车队和比赛状态不能仅靠颜色表达。
- 交互区域至少 48 × 48 dp；图标提供名称和选中状态；键盘与焦点顺序跟随阅读路径。
- 检查 320/360/412 dp 宽度、横屏、系统栏、键盘、TalkBack 与 200% 字号。字号放大时允许换行和行高增长，不硬裁剪。
- 平板优先复用任务结构并按可用宽度分栏；后续 iOS 可共享内容层级与视觉语义，导航和手势仍按 iOS 习惯实现。

## 6. 先设计、再实现的执行顺序

1. **结构设计：**以本文为草案，画出四个主入口与八个页面的低保真流程，标出返回、筛选与权限边界。
2. **可点击原型：**重点验证“首页 → 比赛 → 场次成绩 → 车手表现 → 返回”和“榜单 → 档案 → 返回”。原型示例明确标注，不代表已接入实时数据或原生功能。
3. **视觉设计：**确定 赛事首页、比赛详情、成绩列表和单项分析 四个代表性页面的视觉稿与组件状态。
4. **原生纵向切片：**按新设计实现“赛事 → 比赛 → 成绩”，接真实接口并构建 APK，在手机上验证。
5. **逐项扩展：**按已验证的信息架构增加榜单、资料、账号和分析，首版不保留无法使用的占位导航。

原型完成前不冻结 Kotlin 页面结构；环境与接口核查可同时进行。用户查看的是具体原型和视觉稿，再据反馈调整，不要求先批准抽象的全部细节。

## 7. 设计验收

- 新用户打开首页能识别当前比赛周末与下一步操作。
- 从赛事首页到已发布的正赛成绩不超过两次主要点击，且无需打开侧边菜单。
- 能区分“尚未开始 / 结果未发布 / 无此场次 / 加载失败 / 缓存离线”。
- 返回能恢复列表位置、场次和筛选；刷新不意外改变当前任务。
- 日常成绩查询不需要横向拖动大表或依赖 hover。
- 在 360 dp 宽度下，正文与列表只有一层侧边留白；无包裹每条数据的卡片框、无容器套容器造成的宽度损失。
- 图表所有关键数据可通过触屏和可访问的数据视图读取。
- 原型、视觉稿、真实数据 APK 与设备验证分别记录完成状态，不能互相替代。

本次交付为第一版可点击评审原型及设计约束修订。浏览器检查覆盖 320/360/375/412/768/1440 px 宽度、主导航、成绩与分析路径、返回保留选择、主题与时区、加载/空数据/错误重试/离线状态；无控制台错误或失败请求。详见 `docs/qa/native-app-prototype-2026-10-27.md`。这些结果只验证原型，不代表 Android 字号、TalkBack、真机性能或 APK 已验收。

后续原生实现采用同一视觉方向并读取真实公开接口，首版暂不开放会员分析和图表。其单元测试、构建和签名结果单独记录，不使用原型截图替代设备证据。
