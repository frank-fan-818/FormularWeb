**文档状态**：可执行基线

**最后更新**：2026-08-19  
**目标读者**：产品、设计、前端、数据工程、测试、运维、安全审查者  
**适用平台**：桌面 Web、移动 Web、PWA、Android Capacitor 容器

## 1. 文档目的

本 PRD 定义 FormularOneWeb 的产品定位、用户问题、功能边界、信息架构、页面需求、数据契约、非功能要求、性能预算、异常策略、埋点指标、验收标准和发布策略。任何新功能都必须能够回答三个问题：

1. 它帮助用户更快回答了哪个 F1 问题？
2. 它使用的事实来自哪里，何时过期，失败时如何诚实降级？
3. 它为首屏、交互、网络和维护成本增加了多少预算？

本文是产品层的长期来源；工程实现细节仍以 `docs/engineering-specification.md`、ADR 和代码契约为准。

## 2. 产品摘要

### 2.1 一句话定义

FormularOneWeb 是一个以赛季、比赛周末和历史对象为主索引的 Formula 1 数据产品，让用户在一处完成赛历浏览、积分判断、比赛复盘、车手/车队/赛道研究、遥测分析和预测比较。

### 2.2 核心价值主张

- **快**：用户进入任何页面后，应尽快看到可识别结构、最近可用事实和明确状态。
- **真**：不以 mock 数据伪装实时结果；来源、缺失、陈旧和降级必须可辨识。
- **深**：同一比赛周末从结果延伸到排位、冲刺、策略、天气、遥测和升级信息。
- **可比较**：排名、差距、趋势和历史上下文优先于装饰性卡片。
- **可恢复**：上游、网络、缓存或单个分析模块失败时，其余内容仍可使用。

### 2.3 明确不是什么

- 不是实时转播或版权视频平台。
- 不是投注、交易或保证结果的预测服务。
- 不是新闻编辑部、社交社区或车迷论坛。
- 不是车队内部工程工具；公开数据的精度和延迟必须被如实标识。
- 不是必须登录才能查看的 SaaS；公开赛事数据默认匿名可用。

## 3. 背景与机会

F1 数据分散在赛历、官方分类、历史数据库、遥测处理结果和技术文件中。普通用户需要在多个来源间切换；深度用户又常被“只有图、没有上下文”或“只有表、没有比较”阻碍。产品机会是用稳定的信息架构把分散事实组织成一条连续决策路径：

```text
现在发生什么 → 下一场是什么 → 谁领先 → 为什么领先 →
某场比赛发生了什么 → 哪些数据支持判断 → 历史上如何比较
```

现有 0.13.4 已具备发布候选能力：双分支治理、严格 CI、安全扫描、路由懒加载、服务工作线程、缓存与多视口浏览器 QA。下一阶段的重点不是盲目增加功能，而是把“从打开到获得答案”的总时间压到更低，并让功能深度保持可验证。

## 4. 产品原则

### 4.1 答案优先

每个页面只允许一个首要任务。首屏先给结论、状态或操作入口，再给解释和深度模块。

### 4.2 事实有出处

所有赛事事实必须来自 Jolpica/Ergast、Supabase 只读数据、FastF1 处理结果、FIA 文档产物或明确的本地静态资产。预测必须标记为模型输出，不得与事实分类混淆。

### 4.3 局部失败不扩散

页面由多个资源构成时，资源独立显示 loading / empty / error / stale。一个图表或数据源失败不得清空整个页面。

### 4.4 性能也是功能

如果一个功能让低端移动设备的首屏或路由切换显著退化，它就没有完成。每个新增依赖、图表、图片和请求都必须说明是否属于首屏必需。

### 4.5 可访问与响应式默认成立

桌面、平板和移动端不是后续适配项。键盘操作、语义标题、可读对比度、无横向溢出和可感知状态是验收条件。

## 5. 用户与场景

### 5.1 主要用户 A：赛周快速查看者

- 目标：几十秒内知道下一场时间、当前积分、比赛结果。
- 环境：手机、蜂窝网络、可能只停留一次。
- 痛点：页面重、广告多、日期时区混乱、结果入口深。
- 成功：一次首屏或一次点击得到答案。

### 5.2 主要用户 B：数据型车迷

- 目标：比较车手、车队、轮胎、圈速、排位和比赛表现。
- 环境：桌面或平板，连续切换多个页签。
- 痛点：不同来源口径不一致；图表缺少空状态、单位或上下文。
- 成功：同一比赛上下文中完成多维比较，切页无需重复等待公共数据。

### 5.3 次要用户 C：历史研究者

- 目标：查看车手、车队、赛道的职业历史、赛季与代表成绩。
- 环境：搜索直达详情页，路径可能来自旧链接。
- 痛点：历史 ID/名称变化、数据缺失、请求数量巨大。
- 成功：直达页面仍能解析身份，核心履历先出现，深度数据渐进补齐。

### 5.4 次要用户 D：项目维护者

- 目标：安全增加数据和页面，清楚知道是否可以发布。
- 成功：PR 自动获得类型、测试、安全、性能和浏览器证据；生产分支始终可部署。

## 6. 核心用户旅程

### 6.1 今日赛况旅程

1. 用户打开首页。
2. 首屏看到当前赛季、赛季进度、榜首、下一信号。
3. 若有进行中比赛，进入比赛解读；否则进入下一场周末情报。
4. 页面保留赛季上下文，并展示结果、排位、分析、冲刺、情报页签。
5. 单个模块无数据时，仍可切换其他页签。

### 6.2 赛季研究旅程

1. 用户进入赛季页或赛历页。
2. 切换年份。
3. 查看积分、完赛进度与各分站。
4. 进入某场、车手或车队详情。
5. 返回后保留赛季选择和浏览上下文。

### 6.3 搜索直达旅程

1. 用户激活全局搜索；搜索代码只在意图出现后加载。
2. 输入车手、车队、赛道或比赛关键词。
3. 结果只能导航至通过同源边界验证的内部路径。
4. 详情页先展示身份和概要，再补充历史/图表。

### 6.4 离线/弱网旅程

1. 应用壳从 Service Worker 或浏览器缓存启动。
2. 页面优先显示最近缓存数据并标明离线或陈旧。
3. 未缓存模块显示具体空状态，不无限旋转。
4. 网络恢复后允许主动重试或后台刷新。

## 8. 页面级详细需求

### 8.1 全局应用壳

**首要任务**：在不遮挡内容的情况下提供导航、赛季、语言、主题、搜索和账号入口。

**必须**：

- 当前路由有明确选中状态。
- 移动侧栏可关闭、滑动关闭且不造成横向溢出。
- 搜索模块在点击、聚焦或指针意图后才下载。
- 导航意图可在非省流/非 2G 网络预取目标路由模块。
- 主题在 React 首次绘制前尽可能确定，避免明暗闪烁。
- 赛季选择在比赛详情中保留查询参数语义。

### 8.2 首页

**首要任务**：五秒内判断“本赛季现在最重要的四个信号”。

**首屏必须**：赛季、完成进度、车手榜首、车队榜首、下一场/当前场状态。  
**渐进内容**：下一场详情、Top 3、统计卡。  
**异常**：三个赛季资源独立状态；有任何缓存数据时不得用全页错误覆盖。  
**交互**：下一场卡在 hover/focus 时预取比赛容器与情报页。

### 8.3 赛季积分页

**首要任务**：快速比较车手和车队积分。  
**要求**：排名、积分、差距、车队身份语义明确；切换赛季取消/忽略过期请求；大表在视口外延迟实例化；移动端保持名称和积分可读。

### 8.4 赛历页

**首要任务**：按状态与时间找到目标分站。  
**要求**：已完成、进行中、未来状态统一；时区显示一致；比赛卡可键盘激活；意图预取比赛默认页。

### 8.5 比赛周末容器

**首要任务**：一次加载比赛公共上下文，多页签复用。  
**要求**：公共比赛信息、结果发现、会话可用性和诊断 flow ID 由 Provider 统一管理；页签模块独立懒加载；切换页签时预取邻近模块；冲刺页签只在有证据时出现。

### 8.6 结果、排位、冲刺

- 表格必须拥有加载骨架、空态和错误态。
- 大型 Ant Table 仅在接近视口时加载。
- 排位/冲刺图表只在存在可绘制数据时下载 ECharts。
- 排名、状态、退赛和无成绩不得用相同视觉语义。

### 8.7 比赛分析

**首要任务**：从数据解释比赛，而不是堆叠图表。  
**内容优先级**：关键洞察 → 位置/圈速 → 轮胎与策略 → 遥测 → 天气/赛道状态。  
**性能**：图表库按视口延迟；非首屏区块采用渲染隔离；不可一次性挂载所有 canvas。  
**可信性**：每张图标单位、样本范围和空数据原因。

### 8.8 车手、车队、赛道列表与详情

- 列表首屏先显示可搜索身份，不等待非关键装饰资产。
- 详情身份头与职业概要优先；历史聚合和图表渐进加载。
- 历史别名/ID 必须通过可信映射解析，不把用户输入直接拼接到外部 URL。
- 赛道 SVG 按目标赛道动态导入，禁止把全部赛道图形合入首屏。

### 8.9 设置、登录、隐私与 404

- 设置页不得让实验功能影响默认生产路径。
- Supabase 未配置时，登录页明确说明，不发起无意义请求。
- 恢复/重置 URL 中的敏感片段不得进入诊断日志。
- 404 提供回到首页和核心索引的可操作路径。

## 9. 功能需求

### FR-01 赛季上下文

- 默认赛季由 UTC 日期与赛历规则计算，不硬编码过期年份。
- 用户选择持久化；数据迁移必须处理旧版本值。
- 比赛详情查询参数的赛季优先于全局赛季，但不得污染其他页面。

### FR-02 数据获取与降级

- 公共基础数据通过同源 `/f1-api` 访问。
- 增强数据可来自 Supabase；浏览器只使用匿名只读凭据。
- 请求支持超时、有限重试、取消/过期结果忽略。
- 新鲜缓存直接返回；陈旧缓存先显示并后台刷新；无缓存失败才显示错误。

### FR-03 搜索

- 支持车手、车队、赛道、比赛。
- 搜索代码、Supabase 客户端和索引数据不得进入无意图首屏。
- 结果路径经过内部路由安全校验。

### FR-04 比赛分析

- 支持结果、排位、冲刺、圈速、策略、遥测、天气等可用模块。
- 数据不存在和请求失败是不同状态。
- 图表 tooltip 必须转义动态文本并适应移动视口。

### FR-05 预测

- 明确展示模型名称、概率/分数、数据时间和非保证声明。
- 模型输入缺失时不生成伪精确概率。
- 线性、非线性、序列模型使用可比较输出契约。

### FR-06 账号与隐私

- 公开浏览无需账号。
- 可选账号支持登录、注册、重置、恢复和退出。
- 诊断写入只允许认证用户写入自己的脱敏记录。

### FR-07 离线与版本更新

- 静态壳和内容哈希资产可离线读取。
- 公共 GET 数据采用有界 stale-while-revalidate 缓存。
- 多标签页升级不得删除仍被旧客户端使用的壳缓存。
- stale chunk 恢复最多在时间窗内执行一次，避免刷新循环。

## 10. 数据需求与契约

### 10.1 核心实体

`Season`、`Race`、`Circuit`、`Driver`、`Constructor`、`RaceResult`、`QualifyingResult`、`SprintResult`、`Standing`、`SessionAnalytics`、`FiaCarUpgrade`、`Prediction`。

### 10.2 数据质量规则

- 列表总数与上游 `total` 一致时才视为完整。
- 赛季轮次应连续或有明确缺失说明。
- 车手/车队/轮次主键在响应中唯一。
- 数值解析失败显示 `-`，不默认为零。
- 历史事实一旦完赛可长缓存；当前赛季采用短缓存和后台刷新。

### 10.3 来源优先级

| 数据 | 首选 | 降级 | 禁止 |
| --- | --- | --- | --- |
| 官方赛历/积分/分类 | 项目数据库或 Jolpica | 最近可信缓存 | 伪造实时数据 |
| FastF1 分析 | 处理后的静态/数据库产物 | 空态解释 | 浏览器现场执行重计算 |
| FIA 升级 | 解析后的结构化产物 | 原文引用/空态 | 未验证 LLM 生成事实 |
| 预测 | 已版本化模型 | 不展示 | 冒充官方结果 |

## 11. 非功能需求

### 11.1 性能 SLO

以下均以生产构建、冷缓存、移动 Lighthouse 默认模拟为基线，五次取中位数；真实用户指标以 p75 为准。

| 指标 | 发布阻断目标 | 卓越目标 |
| --- | ---: | ---: |
| Performance score | ≥ 0.95 | ≥ 0.98 |
| FCP | ≤ 1.8 s | ≤ 1.5 s |
| LCP | ≤ 2.3 s | ≤ 2.0 s |
| TBT | ≤ 150 ms | ≤ 50 ms |
| CLS | ≤ 0.05 | ≤ 0.02 |
| INP（RUM p75） | ≤ 200 ms | ≤ 120 ms |
| 初始 JS gzip | ≤ 100 KiB | ≤ 85 KiB |
| 首页关键 JS gzip | ≤ 110 KiB | ≤ 95 KiB |
| 最大异步 chunk gzip | ≤ 135 KiB | ≤ 110 KiB |
| 意图预取后的路由切换 | ≤ 300 ms | ≤ 150 ms |
| 热缓存公共数据响应 | ≤ 100 ms | ≤ 30 ms |

性能预算不得通过关闭功能、隐藏错误、降低可访问性或删除质量门禁“达成”。

### 11.2 可用性

- 静态壳目标月可用性 99.9%。
- 单个上游不可用时，缓存或局部错误必须保持导航可用。
- 每个可失败操作提供重试或明确下一步。

### 11.3 安全与隐私

- 禁止提交密钥、环境文件和私钥。
- CSP、HSTS、nosniff、frame deny、权限策略必须保留。
- 浏览器不得持有 service role key。
- 动态 HTML tooltip 必须转义；禁止危险 `eval` 和未审查 `innerHTML`。
- 日志不记录 token、密码、完整恢复 URL 或敏感查询参数。

### 11.4 可访问性

- Lighthouse Accessibility ≥ 0.95。
- 键盘可达、焦点可见、标题层级合理、状态具有 ARIA 语义。
- 颜色不是唯一状态编码；尊重减少动画偏好。

### 11.5 兼容性

- 支持当前及前一主版本 Chrome/Edge/Safari/Firefox。
- 视口基线：1440×900、768×1024、375×812。
- 不支持的高级性能能力必须渐进增强，不得阻断基本内容。

## 12. 加载体验规范

### 12.1 状态机

```text
无缓存 + 请求中 → skeleton
新鲜缓存 → 立即内容
陈旧缓存 + 刷新中 → 内容 + freshness notice
部分资源失败 → 已有内容 + 模块级错误
全部失败且无缓存 → 页面级错误 + 重试
离线且有缓存 → 内容 + offline notice
离线且无缓存 → 可导航壳 + 具体空态
```

### 12.2 骨架要求

- 骨架尺寸接近最终内容，避免 CLS。
- 不为小于约 150ms 的操作闪烁骨架。
- 不用全屏 spinner 遮挡已经可用的内容。

## 13. 指标与可观测性

### 13.1 产品指标

- 首页到比赛详情点击率。
- 比赛页签切换深度。
- 搜索激活率、成功导航率、无结果率。
- 缓存命中后可用内容时间。
- 模块级错误率与重试成功率。

### 13.2 性能指标

- Web Vitals：TTFB、FCP、LCP、CLS、INP。
- 维度：pathname、设备类别、连接类型、是否缓存、应用版本。
- 不记录用户搜索原文或敏感标识。

### 13.3 诊断日志

- `entry`：调用来源、参数概要、时间。
- `step`：数据源、阶段、耗时、结果。
- `exit`：总耗时、成功/失败、reason code、flow ID。

## 14. 成功标准

### 14.1 用户成功

- 首页无需滚动即可回答当前赛季四个核心问题。
- 任意核心路由在弱网下先呈现结构，不出现长时间空白。
- 公共数据源失败时，缓存用户仍能完成主要任务。
- 移动端无横向溢出，关键数字和操作不重叠。

### 14.2 工程成功

- `quality:check` 全绿。
- 所有新增加载策略有单元或策略测试。
- Lighthouse 五次中位数满足阻断目标。
- 包体预算比 0.13.4 基线更严格，不能回退。
- 浏览器 QA 覆盖六个核心路由、三类视口和控制台/网络失败。

## 15. 发布与回滚

1. 功能分支合入 `develop`。
2. `develop` 通过安全、Lint、类型、测试、构建、预算、Lighthouse、浏览器 QA。
3. 创建 `develop → main` PR；`main` 六项检查全部通过。
4. 部署精确 commit，并验证缓存头、Service Worker build ID、API rewrite 和核心路由。
5. 保留上一生产部署为回滚目标。
6. 性能若出现显著回退，优先关闭可独立回滚的预取/缓存策略，不回滚数据正确性修复。

## 16. 风险与约束

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| SPA 无 SSR | 搜索引擎首屏依赖 JS | 保持静态元信息；若内容 SEO 成为核心再单独 ADR |
| 公共 API 波动 | 首次用户无数据 | 边缘缓存、SW stale-while-revalidate、局部降级 |
| 过度预取 | 浪费流量/挤占关键请求 | 仅 intent 触发；尊重 Save-Data/2G；去重 |
| 缓存陈旧 | 用户误读 | 当前赛季短 TTL、时间标识、后台刷新 |
| 图表库较大 | 深度页加载慢 | 视口延迟、按组件注册、模块分块 |
| 过度代码分割 | 请求瀑布 | 以用户路径为单位分块，避免极小碎片与串行 import |
| 单人 PR 审批 | 无法自审 | main 要求 PR+CI，不要求外部审批；对抗性自动审查补位 |

## 17. 对抗性验收问题

发布审查者必须尝试证明产品“不该发布”：

- 关闭网络、清空缓存、限速、禁用 Supabase，各页面发生什么？
- 快速切换赛季和路由，旧请求是否覆盖新结果？
- 连续 hover 所有导航是否造成下载风暴？
- Save-Data 或 2G 是否仍偷偷预取大图表？
- Service Worker 中缓存了 HTML 错误页、登录响应或非 JSON 吗？
- API 返回空数组、部分列表、重复主键、错误 content-type 时如何表现？
- 低端 CPU 下是否因一次挂载多个表/图而阻塞交互？
- 动态 chunk 更新后，多标签页是否进入刷新循环？
- 去掉 JavaScript 后是否仍有基本标题、描述和隐私入口？
- 包体预算能否被新增依赖轻易绕过？
