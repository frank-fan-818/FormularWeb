## ADR-005：FIA 赛车升级文档解析 — 正则+规则引擎而非 LLM

- **背景**：FIA 每站比赛后发布 PDF 文档，描述各车队的赛车升级情况（部件类别、升级原因、性能影响）。需要将这些非结构化 PDF 内容提取为结构化数据存入 Supabase。两种方案：传统正则+规则解析，或使用 LLM 进行提取。
- **选项**：
  - A：**正则 + 规则引擎** — 优点：确定性输出（相同输入永远相同结果）、零 API 成本、可本地运行、可做精确的单元测试。缺点：需要为每种文档格式编写规则、FIA 改格式时可能失效
  - B：**LLM（如 Claude）提取** — 优点：对格式变化更鲁棒、能理解上下文语义。缺点：每次调用有成本、输出有随机性、需要 Evals 验证、依赖外部 API 的可用性
  - C：**正则 + LLM 降级** — 正则优先，匹配失败时降级到 LLM
- **决策**：选择 A — 纯正则+规则引擎。目前代码中 `src/api/fiaCarUpgrades.ts` 和 `src/utils/fiaCarUpgrades.ts` 使用正则表达式 + 关键词匹配 + 规则函数（`normalizeUpgradeReason` / `inferUpgradeComponent`）实现解析。
- **原因**：FIA 技术文档格式相对固定（表格化、术语标准化），正则表达式足够覆盖。确定性解析保证了数据质量（不会有 LLM 幻觉）。当前处理的数据量不大（每站 ~20 个升级条目），正则的维护成本低于 LLM 的调用成本和 Evals 成本。如果未来 FIA 改变文档格式，只需更新规则函数，不需要重新验证 LLM 输出质量。
- **代价**：如果 FIA 大幅改变文档格式（如改用纯散文描述而非表格），现有的正则规则可能需要大量重写。但此时可以改为 C 方案，引入 LLM 作为降级路径。当前阶段正则方案是最务实的选择。
