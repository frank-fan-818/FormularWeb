# 从“能打开”到“更快拿到答案”：一个 F1 数据网站的性能迭代心得

做 FormularOneWeb 的这几个月，我对“响应速度”的理解一直在变。

这个网站从 F1 赛程、车手和车队积分榜起步，逐渐加入历史成绩、赛道资料、FastF1 遥测、比赛分析和会员功能。功能越来越多，页面需要处理的代码、数据和状态也越来越多。回头翻看 2026 年 4 月到 9 月的 Git 记录，我发现性能优化几乎贯穿了整个开发过程。

它没有一次完成。减少重复请求之后，大文件成了问题；拆完大文件，缓存又带来了旧资源；首屏压下去之后，新增功能又把重依赖带了回来。

这些迭代让我逐渐形成一个判断：**用户等待的时间，取决于我们把多少工作安排在了他获得答案之前。**

4 月的优化，首先落在数据获取方式上。

当时网站已经有赛季、车手、车队和历史详情等页面。这些页面经常使用相同的数据，如果每个页面都独立请求和计算，用户只是换了一个入口，系统却把工作重新做了一遍。

4 月 22 日的 `e806204c` 开始复用赛季缓存，把详情页中较重的统计延后，并补上历史摘要的回填工具。第二天的 `3dbb6bac` 进一步让历史详情优先读取预先计算好的摘要；摘要缺失时，才加载跨赛季查询的回退路径。

这件事改变了我看待历史统计的方式。生涯胜场、领奖台次数等信息，并不需要每次有人打开页面时，再由浏览器把原始数据重新汇总。能够提前生成的结果，就应该有一个直接读取的入口，同时保留数据缺失时的恢复路径。

随后，`7b862693` 把列表页的数据获取拆得更细：车手列表读取车手积分榜，车队列表读取车队积分榜，赛道列表复用赛程。一个通用 Hook 用起来方便，但如果页面只需要其中一部分，它也可能让页面承担不必要的请求和等待。

我从这一阶段学到的，是先看清页面到底需要什么。缓存的粒度和请求的粒度，都应该贴近用户正在做的事情。

同一时期，我也开始清理首次打开网站时必须下载的代码。

4 月 22 日的 `390c909b` 把全局搜索拆成懒加载组件：用户点击或聚焦搜索入口时再启用，鼠标移入时可以提前加载。首页的一些简单展示也改用原生元素实现。5 月 1 日的 `6bd1b611` 则把赛道 SVG 从 eager 导入改成按需加载，并复用加载结果。

这些改动的共同点，是重新安排功能出现的时间。搜索很有用，赛道图也很有用，但它们未必都需要参与首页的第一次渲染。

资源本身也值得检查。5 月 31 日，车手头像和车队 Logo 改为随站点提供的静态图片；提交记录中，多数车手头像经过尺寸处理，从约 150–220 KB 缩小到约 15–18 KB。这样既减少了文件体积，也减少了运行时对外部图片服务的依赖。它仍然需要网络传输，不能简单称为“零延迟”，但加载路径更可控了。

到了 6 月，优化开始触及数据文件的结构。

FastF1 分析带来了速度、位置等遥测采样。它们适合详细分析，却不应该成为用户查看比赛概览的前提。6 月 4 日的 `274f9514` 把遥测从主分析 JSON 中拆到独立的 `R-telemetry.json`，在用户打开相关分析功能时再加载；6 月 5 日的 `836add55` 把已有数据迁移到这种结构。

原来的访问方式接近于：先把整份分析资料拿齐，再开始展示。拆分之后，概览可以读取较小的主文件，详细遥测由后续操作触发。

提交说明曾用“初始载荷减少 94%”描述这轮改动。这个数字有明确的语境：它描述的是当时主数据文件的估算变化，不能直接换算成“网站快了 94%”，也不能代表所有比赛文件都有相同收益。对我来说，更值得保留的是这次边界调整——**把首屏需要的数据和深入分析需要的数据分开。**

接下来，数据本身也做了瘦身。`27aca79e` 将遥测采样由对象数组改成列式数组，并把导出器的默认采样数从 650 调整到 250。对象数组会在每个采样点重复字段名，列式结构把同一字段的值集中存放，可以减少这种重复。

6 月 5 日的 `035f3d5e` 又清理了已有遥测文件中的重复摘要和重复字段。按 Git 对象中的实际文件大小核对，这 96 份文件的未压缩总量从 269,107,213 字节降到 135,400,779 字节，约减少 49.7%。这是整个文件集合的变化，不是一次页面访问的下载量；HTTP 压缩后的收益也需要另行测量。

这轮优化还提醒我，体积变化必须拆开解释。删除重复字段、改变存储格式，以及减少采样点，是不同的操作。前两者着重减少冗余，减少采样则涉及细节保留的取舍，不能把它们都包装成没有代价的压缩。

也是在 6 月，积分榜、赛程、正赛和排位赛结果陆续加入 Supabase 优先读取的路径，缺失时再回退到 Jolpica，并由预取脚本同步数据。这让访问路径有机会复用已经准备好的结果，但也引出了下一个问题：结果什么时候失效，谁来更新？

缓存开始成为整个迭代里最有教育意义的部分。

6 月 28 日的提交非常密集：旧 JavaScript 分块在发布后出现 404，随后加入恢复逻辑、调整 Service Worker 更新行为、缩小预缓存范围，最后在 `548e159c` 中移除了 Service Worker。

这段历史让我意识到，缓存的收益不能只看命中率。旧页面、新部署、旧缓存和已经删除的分块一旦混在一起，用户可能连页面都打不开。对这样的访问来说，少一次下载根本没有意义。

后续迭代又重新引入并约束了 Service Worker。回头看，这个过程更像是在重新确定它的职责：哪些资源可以缓存，哪些响应不能写入，缓存是否有界，多标签页如何升级，旧分块失效时如何恢复。

7 月的另一条主线，是把“等待所有数据”改为“独立区域分别就绪”。

7 月 12 日的 `be4ae636` 完善了分层缓存、请求合并和失败恢复。页面可以先显示仍可使用的缓存快照，再刷新数据；独立资源并发获取，一个资源失败不必让整个页面空白。缓存写入失败，也不能把已经成功的网络请求变成页面错误。

这里还有一个容易被忽略的细节：用户快速切换赛季时，旧请求可能比新请求更晚回来。代码通过请求代次等检查，阻止过时结果覆盖当前页面。等待时间再短，如果最后显示的是上一个赛季，也没有完成用户的任务。

图表和重型表格则继续延迟加载，在接近可视区域时再初始化。这些改动让我开始区分两件事：整页所有工作完成的时间，以及用户已经能够使用主要内容的时间。后者更贴近实际体验。

到了 8 月，优化变得更系统，也开始有更清晰的测量口径。

8 月 13 日，新增的数据流诊断处理被移出关键路由路径。这个案例很有意思：诊断能帮助定位问题，但它也可能让被诊断的页面变重。这里并非所有预算从来没有调整过——当时 Race Info 的门槛从 340 KiB 调整到 341 KiB。记录这些细节，比事后把过程写成一条完美曲线更有价值。

8 月 23 日的 `e6cac1e6` 则进行了一轮覆盖全站加载路径的优化：用较小的实现承担项目实际需要的页面元信息和国际化能力，延后性能采集与错误上报实现，按需加载英文资源，并调整路由使用方式，减少没有使用的运行时代码。

图表也做了相同的取舍：只注册需要的 ECharts 图表与组件，直接管理实例的更新、尺寸变化和销毁。入口与首页关键样式在构建时内联，首屏以下区域使用 `content-visibility` 降低提前布局的成本。主要内容保持首帧可见，避免入场动画让内容已经准备好却仍然看不见。

这轮报告记录了以下结果，JavaScript 体积均采用 gzip 口径：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 初始 JavaScript | 120.0 KiB | 82.6 KiB |
| 首页完整静态依赖路径 | 120.0 KiB | 89.6 KiB |
| Race Info 关键路径 | 340.3 KiB | 304.9 KiB |
| Race Analysis shell | 460.6 KiB | 424.3 KiB |
| Lighthouse 五轮性能中位数 | 0.97 | 0.97 |

初始 JavaScript 减少了约 31.2%，但 Lighthouse 性能分数没有随之提高。报告中的 FCP、LCP 也主要表现为稳定，而非同等比例下降。

这让我更愿意尊重指标的边界。包体告诉我传输了多少代码，LCP 告诉我主要内容何时出现，它们之间有联系，却不能互相替代。这轮工作减少了必要传输，也为后续功能留下了一些空间；至于不同网络和设备上的用户到底快了多少，还需要真实用户数据验证。

在这之后，初始 JavaScript 的 85 KiB 预算进入了持续检查。性能优化开始有了一个可以阻止回退的约束。

8 月 25 日的 `2f07ba27` 继续处理点击详情后的等待。

车手和车队详情需要人物资料、赛季成绩和冲刺赛结果。已经知道实体 ID 时，成绩请求就可以提前开始，不必等资料查询全部结束。列表入口还会根据用户意图预取详情模块、图表组件和相关数据，并通过 Promise 缓存复用请求；请求失败后会删除对应缓存项，以便后续重试。

赛道库的元数据请求也不再等待赛程返回后才启动，同时先利用已有静态资料补齐可展示内容。数据和模块没有因此消失，但原先不必要的先后顺序被拆开了。

我开始习惯在写下一个 `await` 之前，确认后面的工作是否真的依赖前面的结果。这个问题往往比“再加一个 loading 动画”更有帮助。预取也需要边界，因此网络节省模式和较慢网络下会限制预取，避免提前工作反过来争抢当前页面的资源。

9 月，缓存的新鲜度又给这套系统上了一课。

9 月 7 日的调查复现了一个问题：Service Worker 可以立即返回赛前缓存的空成绩，随后在后台取到新成绩，但当前 React 请求并不会自动收到那份后台结果。网络请求看起来很快，用户却没有得到新的比赛结果。

`7c0c6c72` 将公共 F1 API 的这一层策略改为优先等待网络，只在网络或 HTTP 失败时回退缓存，并加入构建后 Service Worker 回归测试。事故记录也保留了证据边界：缓存缺陷得到复现，但没有检查到用户当时浏览器的实际响应，不能断言那次现场一定只有这一个原因。

这是我对“快”理解得更完整的一次。历史资料可以容忍较长的复用周期，刚结束的比赛成绩却需要更重视更新。缓存策略需要服从数据用途，而且 Service Worker 的调整也不能自动保证 CDN、应用内缓存等其他层都已经足够新鲜。

最后一次很典型的回退，发生在会员功能加入之后。

9 月 16 日加入认证与私有分析后，根部认证 Provider 静态引用了 Supabase SDK，又通过私有缓存清理逻辑带入 FastF1 API 校验依赖。首页的预测功能也带入了认证请求相关代码。几个局部上合理的引用，合在一起却扩大了公共页面的初始依赖。

CI 报告记录的初始 JavaScript 达到 162,804 gzip 字节，约 159.0 KiB，超过 85 KiB 预算。

9 月 17 日的 `eb449af7` 没有提高这个门槛。它把缓存容器和失效操作拆到没有运行时重依赖的模块，将配置读取与 Supabase 客户端分开，并让 SDK、预测请求实现和登录操作所需代码按实际需要加载。

尤其值得保留的是：清理私有缓存仍然同步执行，还会让正在进行的旧请求失效。代码拆分没有成为推迟清理用户数据的理由。

修复后的记录显示，在与 CI Build 对齐、Supabase 环境配置为空的生产构建中，初始 JavaScript 为 77.2 KiB，首页完整静态路径为 91.7 KiB，既有预算全部通过。这个数字有自己的构建条件，不能直接与此前报告拼成一条严格可比的线上提速曲线。

同期 Lighthouse 五轮性能中位数为 0.93，也低于 8 月报告的 0.97。没有控制所有变量的前后对照，我不会把它解释成某一个改动单独导致的变化。但它足以提醒我：首屏包体达标和整体体验优秀，需要分别检查。

回看整个过程，我最想保留下来的习惯，是每次扩展功能时都问清楚三件事：这部分工作何时才需要开始，结果能否安全复用，失败后已经可用的内容能否继续留在页面上。

历史摘要把重复计算提前完成，按需加载让详细遥测离开概览的等待路径，并发请求消除了不必要的串行，可靠性处理让局部失败不再轻易拖垮整页。性能预算则让新功能带来的额外成本及时暴露出来。

下一步，我更想补齐真实用户环境下的观察：不同设备和网络中的 p75 LCP、详情页主要内容就绪时间，以及赛后成绩从上游发布到页面可见的延迟。仓库已经能告诉我做过哪些优化；用户实际少等了多久，还需要持续测量。
