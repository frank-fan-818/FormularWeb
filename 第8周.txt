第8周：系统的免疫系统——可靠、可观测、可维护
第7周你把流水线搭起来了，系统能跑了。
但"能跑"和"能活"之间，隔着真实用户、脏数据、接口超时、大模型漂移……
本周你要给系统装上免疫系统：出了事能发现，扛得住不崩溃，三个月后别人接手看得懂。
课前你可能会问
"我的项目能跑，还需要加日志吗？加了有什么用？"
"AI 输出每次都不一样，我怎么知道它到底好不好？"
"接口偶尔超时，我只要重试就行了吧？"
"ADR 是什么？我为什么要把决策写下来？"
下面六节逐一回答。记住一句总纲：
系统质量不是上线那一刻的状态，是持续运营中不崩溃、出事后能找到原因、改了代码后别人能看懂你为什么这样改。

1.2 可维护性第一步：日志——没有日志的系统是黑盒（约12分钟）
为什么日志比你以为的重要？
你现在调试的方式大概是：console.log 打一堆，出错了看一眼，修完了删掉。
问题是：部署之后，你打的 log 都不在了；用户出现问题，你完全不知道发生了什么。
生产级日志的最小要求，不是「记录越多越好」，而是一条请求从进来到出去，能还原它的轨迹：
日志链路的三层结构（现代 LLM 应用的可观测性标准）：
请求进入
  └─ 接口日志：user_id / action / duration / status
       └─ 工作流日志：step=classify / input_token=512 / output={"category":"证件"}
            └─ LLM 调用日志：model=deepseek / latency=1.2s / prompt_version=v3
这三层叫做分布式追踪（Distributed Tracing）——即使你现在不用 Langfuse 这类工具，在代码里按这三层打 log，效果是一样的。
怎么在 Trae 里快速补日志？
把你的核心接口路由复制进 Trae，说：
为这个接口路由补充统一日志：
- 请求进入时记录 user_id、action、输入参数概要
- 每个关键步骤完成时记录耗时
- 失败时记录错误类型和具体原因
- 日志格式统一为 JSON，便于后续查询
不修改业务逻辑，不修改接口契约字段。
日志是你的侦探工具——没有日志的系统出了事，你只能靠猜；有了日志，你是在看证据。
图题：日志三层链路——请求→工作流→LLM调用，每层像探照灯
1.3 可靠性：韧性四条铁律（约15分钟）
来自 Release It!（Michael Nygard）的核心观点：
系统不是会不会出故障的问题，而是出了故障之后整个系统会不会一起死。
外部 API 会挂、大模型会超时、数据库会抖——这不是意外，是常态。好的系统不是「永远不出问题」，而是出了局部问题，其他部分还能活着。
铁律一：外部调用必须有 Timeout（超时上限）
没有 timeout 的外部调用，等于把你的系统命运交给别人：
# ❌ 没有超时——如果 OCR 服务卡住，整个请求永远等待
result = ocr_service.recognize(image)
# ✅ 有超时——3秒没回来就放弃，返回友好提示
result = ocr_service.recognize(image, timeout=3.0)
if result is None:
    return {"status": "error", "message": "识别服务暂时不可用，请稍后重试"}
你的项目里所有外部调用（大模型 API、第三方服务、数据库写入）都需要加 timeout。
铁律二：重试要有上限，避免「重试风暴」
重试是好事，但无限重试会让故障放大——你一个服务挂了，所有客户端都在疯狂重试，把服务彻底压垮：
MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    try:
        result = llm_api.call(prompt, timeout=5.0)
        break
    except TimeoutError:
        if attempt == MAX_RETRIES - 1:
            result = FALLBACK_RESPONSE  # 进入降级
            break
        time.sleep(2 ** attempt)  # 指数退避：1s, 2s, 4s
铁律三：AI 功能必须有降级兜底
大模型 API 限流或挂了，不代表你整个产品挂了——AI 功能要能优雅降级：
金句：降级不是失败，是设计——你提前想好了「AI 不工作时，用户还能干什么」。
铁律四：重任务不能阻塞用户主流程
第7周讲过异步，这里再强调一次工程纪律：大模型调用、文件处理、批量任务，默认放后台，前端立刻返回「处理中」，任务完成后更新状态表（第7周的 tasks 表就是这个用途）：
用户点击「上传并识别」
  → 前端立刻看到「已收到，识别中…」（不卡住）
  → 后台：OCR → 分类 → 写库（异步）
  → 状态表更新 status=done
  → 用户刷新或 WebSocket 推送，看到结果
图题：韧性四条铁律——Timeout / 重试上限 / 降级 / 异步不阻塞
1.4 最小 Evals：AI 输出靠不靠谱，靠数据说话（约10分钟）
你现在验证 AI 功能的方式大概是：「我试了几次，感觉还行。」
问题是：「感觉还行」不是工程证据。大模型输出有随机性，今天好明天可能变差；Prompt 改了一个词，输出质量可能大幅变化。你需要一种可以重复、可以量化的验证方式——这就是 Evals（评测）。
为什么传统断言不够用？
传统测试：输入 A → 期望输出 B（完全匹配）
LLM 输出：输入 A → 输出「差不多是 B 的意思」（语义相近，字面不同）
所以 LLM Evals 有两种策略：
最小 Evals 实操流程（本周要求）：
# 第一步：准备 10-20 条测试输入（来自你的真实业务场景）
test_cases = [
    {"input": "丢失了一个黑色钱包，里面有校园卡", "expected_category": "证件/卡片"},
    {"input": "找到了一副蓝色耳机，AirPods样式", "expected_category": "电子设备"},
    # ... 更多案例
]
# 第二步：批量跑，记录每次输出
results = []
for case in test_cases:
    output = your_llm_function(case["input"])
    results.append({
        "input": case["input"],
        "output": output,
        "expected": case["expected_category"],
        "format_ok": "category" in output,  # 确定性检查
        "match": output.get("category") == case["expected_category"]
    })
# 第三步：统计
pass_rate = sum(r["match"] for r in results) / len(results)
format_rate = sum(r["format_ok"] for r in results) / len(results)
print(f"格式合规率: {format_rate:.0%}  分类准确率: {pass_rate:.0%}")
改了 Prompt 之后，重跑一次 Evals，对比数字——这就是工程意义上的「Prompt 版本管理」。
你对 AI 输出的信心，应该来自数字，而不是感觉。跑一遍 Evals，是把「我觉得不错」变成「准确率 87%」。
图题：Evals 三步——准备测试集、批量跑、看数字
1.5 可维护性第二步：ADR——把决策写下来（约8分钟）
一个真实场景：
你三个月后回到项目，看到一段代码：「为什么失物分类要同步调用大模型，而不是异步？」「为什么选了 Supabase 而不是 MongoDB？」「这个 timeout 为什么是 3 秒而不是 5 秒？」
你不记得了。队友也不知道。AI 也猜不到。
ADR（架构决策记录）就是解决这个问题的工具。 它来自《软件架构基础》（Neal Ford，2025 版），是工业界区分「初级工程师」和「能独当一面的工程师」的标志之一。
ADR 的五段式模板（极简，不超过一页）：
## ADR-N：[一句话描述这个决策]
- **背景**：为什么需要做这个决策？当时面临什么约束或压力？
- **选项**：有哪些可能的方案？（列 2-3 个即可）
- **决策**：最终选了哪个？
- **原因**：为什么选这个而不是其他？（这是最重要的一行）
- **代价**：这个选择的缺点或局限是什么？
第8周课件的一条真实 ADR 示例：
## ADR-2：失物分类采用同步 LLM 调用而非异步队列
- **背景**：失物识别是用户上传后立刻需要看到分类结果的功能，延迟直接影响体验
- **选项**：A) 同步调用（用户等待）；B) 异步队列（用户先看「分类中」）
- **决策**：选 A，同步调用，设 3 秒 timeout + 降级文案
- **原因**：当前日活不超过 50，用户对实时分类有强期望；异步方案需要 WebSocket 推送，复杂度超过当前阶段
- **代价**：用户偶尔等待最长 3 秒；若大模型限流，降级体验较差
每位同学第9周路演时，必须展示 ADR-2（本周新增）。 ADR-1 是第5周写的架构决策，ADR-2 是本周最重要的质量/韧性决策。
代码告诉机器怎么做，ADR 告诉人类为什么这样做——这是「可维护性」支柱最直接的工程产物。
图题：ADR 五段式——背景/选项/决策/原因/代价
1.6 可扩展性引子：你的系统增长10倍，先哪里挂？（约5分钟）
这节不求讲深，只种一颗「提前想到增长」的种子。
用一道思考题打开视野：假设你的校园失物平台，从50个日活变成5000个日活——
DDIA 最重要的提醒：可扩展性不是「加了机器就能扩」，而是你的数据模型、索引设计、同步/异步决策，从第一天就在为未来的增长负债或投资。
这不是要你现在去做读写分离或 CDN，而是让你在做架构决策时，养成问一句「如果用户增长10倍，这里会先挂吗？」的习惯——这是 ADR 里「代价」那一行应该回答的问题。
金句：可扩展性不是以后的问题，是今天的设计习惯——你现在问自己「增长10倍先哪里挂」，就是在为未来投资。
